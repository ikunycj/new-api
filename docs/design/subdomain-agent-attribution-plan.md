# 二级代理域名归因方案

## 1. 目标

为被管理员指定的销售或代理提供专属入口，例如：

```text
https://a.ikun.love
```

用户通过该入口注册时，系统能够识别 `a` 对应的邀请者，并记录新用户属于该邀请者。

本方案只增加“二级域名归因”能力，不改造、不迁移、不重定义现有邀请码体系。

归因优先级如下：

```text
用户显式提供的邀请码
    >
二级域名对应的邀请者
    >
无二级域名归因
```

如果用户同时填写了邀请码，二级域名归因逻辑不产生归因记录，继续由现有邀请码流程处理。

## 2. 范围与非目标

### 范围

- 配置特定代理使用的二级域名。
- 通过请求 Host 识别二级域名。
- 将已配置的二级域名映射到邀请者用户。
- 在没有显式邀请码时，为新注册用户解析二级域名对应的邀请者。
- 将匹配到的邀请者 ID 传入现有注册归因流程。
- 通过通配 DNS、HTTPS 和反向代理，让主域名与代理域名进入同一个应用。

### 非目标

- 不修改现有邀请码的生成、展示、校验和失效规则。
- 不修改现有邀请码优先级和返利规则。
- 普通注册直接使用域名对应的邀请者 ID；OAuth 跨域跳转使用现有邀请码传递已确定的代理归因，不新增邀请码生成或校验规则。
- 不让普通用户自行创建二级域名。
- 不为每个代理单独部署一套 new-api。
- 不处理普通登录归因，不因为用户登录其他代理域名而重新分配已有归属。

## 3. 关键边界：二级域名是现有邀请关系的备用来源

本功能不新增独立的客户归属体系，而是扩展现有注册归因入口：

- 用户填写邀请码时：完全沿用现有邀请码流程。
- 用户没有填写邀请码、且 Host 匹配某个代理的二级域名时：把该代理用户 ID 作为现有 `InviterId`。
- 后续继续由现有邀请关系、邀请返现和邀请统计处理。

因此，二级域名注册用户会正式纳入现有邀请码返现体系。二级域名只是邀请码缺省时的另一种邀请来源，不改变邀请码本身的生成和校验规则。

如果邀请码字段非空但邀请码无效，也不能回退到二级域名归因，仍应返回现有邀请码无效错误。

## 4. 业务行为

| 访问入口 | 显式邀请码 | 处理方式 |
|---|---|---|
| `ikun.love` | 有 | 完全走现有邀请码流程 |
| `ikun.love` | 无 | 不产生二级域名归因 |
| `a.ikun.love`，且 `a` 已配置 | 有 | 以邀请码为准，不创建二级域名归因 |
| `a.ikun.love`，且 `a` 已配置 | 无 | 将代理 A 作为现有邀请人写入新用户 |
| `x.ikun.love`，且 `x` 未配置 | 任意 | 按普通注册流程处理，不产生二级域名归因 |
| 已有用户登录代理域名 | 不适用 | 不修改任何归属 |

这里的归因只发生在新用户成功注册或首次完成 OAuth 用户创建时。普通登录不执行二级域名归因。

## 5. 数据模型

### 5.1 代理人配置与二级域名

当前项目使用 `AffiliateUserOverride` 保存“邀请返现-代理人”配置，其中域名字段可空且唯一：

```go
type AffiliateUserOverride struct {
	// 现有邀请返现字段...
	AffiliateDomain *string `json:"affiliate_domain" gorm:"type:varchar(255);uniqueIndex"`
}
```

管理员只需输入二级域名前缀，例如 `a`，不必输入 `a.ikun.love`。主域名由系统 `ServerAddress` 确定。保存时将前缀与主域名拼接为规范化完整 Host（例如 `a.ikun.love`），数据库仍保存完整 Host。注册时校验请求 Host 属于该主域名并进行精确匹配。

示例：

| user_id | affiliate_domain |
|---:|---|
| 101 | `a.ikun.love` |
| 205 | `b.ikun.love` |

该字段为空表示该代理人没有启用二级域名。清空字段即可停用，不需要额外的域名映射表。

`AffiliateUserOverride` 记录本身代表代理人身份。即使所有奖励字段和域名都为空，也保留该记录，奖励参数动态跟随全局配置。清空最后一个域名不会删除代理人，修改一个字段也不会把其他跟随全局的字段固化为当前数值。

域名字段必须建立唯一索引，保证一个二级域名只能属于一个邀请者。

### 5.2 归因数据直接复用现有邀请关系

当注册请求没有邀请码并匹配到 `AffiliateUserOverride.AffiliateDomain` 时，使用该行的 `UserID` 作为现有 `InviterId`，然后继续调用现有用户创建和邀请关系流程。

不新增独立的客户归因表，也不改变现有 `AffiliateReferral`、`AffiliateReward` 和邀请返现数据结构。这样二级域名注册用户会自动进入现有邀请返现统计。

## 6. Host 解析规则

后端需要在可信边界内读取请求 Host，并按以下规则处理：

1. 去掉端口，例如 `a.ikun.love:443` 转换为 `a.ikun.love`。
2. 转为小写。
3. 去掉末尾的点。
4. 校验 Host 属于配置的主域名且只有一层代理前缀，先查完整 Host，再查对应前缀。
5. 邀请者用户必须存在，且用户状态符合系统要求。
6. 没有配置域名的邀请者不作为二级域名邀请者。

不要根据 Host 中的文字直接推导用户 ID，也不要信任客户端自定义的 `X-Agent-ID`、`X-Forwarded-Host` 等字段。反向代理应覆盖这些字段，应用只接受来自受控入口的 Host 信息。

建议封装为一个单一解析入口：

```go
func ResolveAffiliateInviterByHost(host string) (int, bool, error)
```

应用层只关心三个结果：

```text
matched = true  -> 返回邀请者用户 ID
matched = false -> 当前请求不是有效代理域名
error           -> 数据库或输入处理失败
```

## 7. 认证归因流程

### 7.1 普通注册

注册请求到达后，流程为：

1. 保留现有注册参数校验。
2. 判断用户是否显式提交邀请码。
3. 如果邀请码非空，跳过二级域名归因解析。
4. 如果邀请码为空，解析当前 Host。
5. Host 对应某个邀请者的 `AffiliateDomain` 时，将该邀请者用户 ID 作为 `inviterId`。
6. 如果 Host 未匹配，使用 `inviterId = 0`。
7. 将 `inviterId` 传入现有用户创建流程。

当 `inviterId` 来自二级域名时，现有 `Insert` 或 `InsertWithTx` 会继续创建 `AffiliateReferral`，并按照现有规则产生邀请返现。二级域名只负责提供邀请者 ID，不新增另一套关系写入逻辑。

### 7.2 OAuth 注册

登录入口统一为：

```text
GET /api/oauth/start/:provider?aff=<显式邀请码，可省略>
```

1. 从代理子域名进入时，显式邀请码优先；没有邀请码才解析当前 Host 对应的代理人。
2. 跳转到 `ServerAddress` 配置的主域名同一入口。域名匹配到的代理人通过其现有邀请码传递，子域名不签发 OAuth session。
3. 主域名生成随机 `oauth_state`，将邀请码和发起时间存入受保护的 session，再跳转到第三方授权页。
4. 授权和换取令牌均使用同一个回调地址：`<ServerAddress>/oauth/<provider>`。LinuxDO、Discord、OIDC 和自定义 OAuth 保持一致。
5. 回调校验 state 及 600 秒有效期，并清除当前 session 中的 state。第三方账号是新用户时才使用该邀请码创建邀请关系；已有用户不重新归因。

登录 session 保持 host-only，第三方登录完成后停留在主域名，不扩大 session cookie 到所有子域名。现有账号绑定入口仍用于账号绑定，不经过会清理登录 session 的登录入口。

微信注册同时写入 `users.inviter_id` 并调用现有邀请关系创建流程，使用户记录与返现关系保持一致。

### 7.3 普通登录不参与归因

密码登录、OAuth 登录和其他普通登录成功后，不创建、不修改二级域名归因。

这样可以保证用户已经注册后，访问其他代理域名不会改变任何历史归属，也不会产生客户争抢问题。

## 8. DNS、HTTPS 与反向代理

### 8.1 DNS

推荐使用通配记录：

```text
A  @  -> 当前入口服务器 IP
A  *  -> 当前入口服务器 IP
```

这样以下地址都会到达同一个入口：

```text
ikun.love
a.ikun.love
b.ikun.love
```

通配 DNS 只是让请求能够到达应用。只有在“邀请返现-代理人”中配置并匹配到 `AffiliateDomain` 时，二级域名才会产生代理归因；未配置的二级域名仍按普通注册流程处理。

如果不希望未配置的域名在 DNS 层解析，可以改为每个代理建立一条精确 DNS 记录，但新增代理时需要同步修改 DNS。

### 8.2 HTTPS

证书需要覆盖：

```text
ikun.love
*.ikun.love
```

主域名和通配子域名都应该使用 HTTPS。证书由 Cloudflare、证书管理平台或 Let's Encrypt 管理均可，关键是代理入口和所有目标域名的证书覆盖范围一致。

### 8.3 Nginx/OpenResty

示例配置如下，`proxy_pass` 需要替换成实际 new-api 上游地址：

```nginx
server {
    listen 80;
    server_name ikun.love *.ikun.love;

    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name ikun.love *.ikun.love;

    ssl_certificate     /etc/letsencrypt/live/ikun.love/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ikun.love/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;

        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

其中最重要的是：

```nginx
proxy_set_header Host $host;
```

如果不保留用户访问的 Host，Go 应用无法区分 `ikun.love` 和 `a.ikun.love`。

## 9. 登录状态与前端体验

DNS 和反向代理完成后，两个地址可以返回同一套前端和 API。但浏览器仍然会把它们视为不同 Origin。

当前实现保持 host-only session cookie，不共享主域名和子域名登录态。普通注册在用户访问的域名完成；OAuth 按第 7.2 节跳到主域名发起并完成登录。

邀请码的 localStorage 不会在主域名和子域名之间共享。本方案不依赖 localStorage 进行二级域名归因，归因以服务端收到的 Host 为准。

如果项目启用了 `FRONTEND_BASE_URL`，需要确认访问 `a.ikun.love` 时不会被统一重定向到另一个前端域名，否则应用会丢失原始代理 Host。

## 10. 代理人管理与统一保存

“邀请返现-代理人”中支持：

- 搜索用户并添加为代理人，新代理默认跟随全局配置，无须先改动参数才能保存。
- 编辑备注、二级域名前缀、返现比例、每位被邀请者返现上限和冻结期。
- 清空二级域名前缀以停用入口，保留代理人及既有邀请关系。
- 在对应代理人的“添加被邀请者”中搜索用户 ID、名称或邮箱，暂存待绑定用户。
- 通过页面右上角一个保存按钮提交所有已修改的代理人和待绑定用户。

批量接口：

```http
PUT /api/affiliate/admin/agents
Content-Type: application/json

{
  "agents": [
    {
      "user_id": 101,
      "override": {"affiliate_domain": "a", "remark": "销售 A"},
      "invitee_user_ids": [301, 302]
    },
    {"user_id": 205, "override": {}}
  ]
}
```

整个请求使用一个数据库事务和一次敏感接口限流额度。任意代理配置或绑定失败，全部回滚；页面保留草稿并显示具体错误。保存成功后清除对应本地草稿和临时添加行，再读取服务端分页，避免已保存行长期固定在所有页面或覆盖最新数据。

人工绑定只允许尚未归属其他邀请者的用户，不允许绑定自己。绑定同时维护 `users.inviter_id` 和 `AffiliateReferral`；重复提交同一关系不重复累计邀请数。人工绑定不发放注册奖励、不补发历史充值返现，绑定之后成功的在线充值才参与现有返现流程。

域名保存时校验：

- 前缀格式合法，完整域名必须属于 `ServerAddress` 对应主域名。
- 不能占用其他代理的域名前缀。
- 用户存在。
- 保留 `www`、`api`、`admin`、`static`、`cdn` 等系统名称。

已停用域名不再为新注册产生归因，历史邀请关系不变。邀请者必须处于启用状态，才会在注册时被识别。

### 自动转入与余额缓存

返现可用后自动转入邀请者钱包。如果转入后会超过钱包上限，返现保留为可用状态，等待钱包有空间后重试，不回滚已支付用户的充值。人工明确发起转入时仍按余额上限返回错误。

自动转入在锁定收款用户和奖励记录的事务内，以“奖励 ID + 累计已转入额度”生成幂等键。原返现到账后再次人工增加的金额可以独立转入；如果因钱包上限暂缓，后续重试不会被原到账记录拦截。重复调账请求和重复结算不会重复入账，已有转入记录无需迁移。

普通返现和现金返现均按奖励 ID 游标分批处理。每处理一条记录就推进游标，包括因钱包上限暂缓的记录；没有更多记录时结束，不能根据本批实际释放数量提前结束。每次任务从头扫描，确保暂缓奖励在后续任务中重试。用户查询余额时的补结算也采用游标分页，避免最早一批暂缓奖励挡住其后的奖励。

在线充值、定时返现释放和人工调账在数据库事务成功后清理受影响用户的 Redis 余额缓存，避免旧余额长期参与后续鉴权与扣费。缓存清理失败记录错误，不伪装为充值事务失败。

## 11. 数据库升级路径

项目当前使用 `DB.AutoMigrate(...)` 维护模型表结构。实现时只需要给 `AffiliateUserOverride` 增加一个可空的唯一字段，并让现有迁移入口补充该列和索引：

```go
// AffiliateUserOverride.AffiliateDomain
```

不新增独立归因表，不重写既有邀请码数据。现有数据库和新数据库都通过同一套 `AutoMigrate` 路径完成字段升级。

## 12. 验证用例

至少需要覆盖：

1. `ikun.love` 不产生二级域名归因。
2. 已配置的 `a.ikun.love` 能解析到正确代理。
3. 未配置的 `x.ikun.love` 不产生归因。
4. 已停用的域名不产生新归因。
5. 用户有显式邀请码时，不创建二级域名归因。
6. 用户无邀请码且使用有效代理域名注册时，现有 `inviterId` 使用匹配的邀请者。
7. 用户通过二级域名注册后，现有 `AffiliateReferral` 正常创建。
8. 二级域名产生的邀请返现使用现有邀请返现规则。
9. 域名停用后，新的注册不再使用该邀请者。
10. 已有用户登录代理域名时，不修改已有邀请关系。
11. Host 带端口、大小写或末尾点号时，解析结果稳定。
12. 并发保存同一个 Host 时，唯一索引能够阻止重复配置。
13. 新代理全部跟随全局时能够保存，并随全局配置变化。
14. 清空仅有的域名配置后，归因停用且代理身份保留。
15. 多代理整批提交时，任一被邀请者冲突会使整批配置与绑定全部回滚。
16. 人工绑定不重复累计邀请数，且不为绑定之前的充值补发返现。
17. 邀请者钱包到上限时，被邀请者充值成功且返现保留可用；余额有空间后可以转入。
18. 自动转入提交后清理受影响用户缓存。
19. OAuth 子域名入口先跳主域名，再签发 host-only session；显式邀请码优先。
20. OAuth state 超时或已从当前 session 消费时拒绝回调。
21. 保存成功后翻页不固定已保存行，新查询不被旧草稿覆盖。
22. 主域名和代理域名都能正常访问前端、API 和流式请求。
23. HTTPS 证书同时覆盖主域名和通配子域名。
24. 已到账返现再次人工增加时，钱包上限暂缓后能够自动恢复转入，重复调账与结算不重复入账。
25. 普通返现与现金返现的首批记录因钱包上限暂缓时，游标仍推进，后续代理的到期奖励正常结算。

其中部署 DNS/HTTPS、真实第三方授权及真实 Redis 缓存验收需在相应环境完成，不能用本地单元测试代替。

## 13. 推荐落地结论

按当前需求，推荐采用：

```text
通配 DNS
    + 主域名和通配子域名 HTTPS
    + Nginx/OpenResty 保留 Host
    + 在邀请返现代理人配置中设置唯一二级域名前缀
    + 注册时将二级域名匹配结果传入现有 inviterId
    + 显式邀请码存在时跳过二级域名匹配
    + 只在注册时归因，普通登录不改变归属
```

这个方案不改变邀请码的生成和校验规则，但会按要求把没有填写邀请码的二级域名注册用户纳入现有邀请关系、邀请返现和邀请统计。
