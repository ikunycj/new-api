# 定价分组动态渠道调度策略设计

> 文档状态：首版已实现，滚动占比保护与跨实例并发租约作为后续增强
>
> 设计日期：2026-08-26
>
> 适用范围：定价分组、API Key 多分组路由、渠道选择、重试与故障转移

## 1. 结论

系统维护一份独立、可复用的命名策略目录。管理员在“策略设置”中新增、修改和删除策略，再为每个定价分组选择其中一个策略；策略不是写死的枚举。

新配置初始化以下三个普通策略记录：

| 策略 | 目标 |
| --- | --- |
| 价格优先 | 优先使用有效价格较低的渠道，同时避免低价渠道过载 |
| 均衡 | 同等关注有效价格和前一天可用性 |
| 稳定 | 以前一天可用性为主要依据，价格作为次要因素 |

这些初始策略以及管理员后续创建的策略共享同一条调度链：

```text
权限、能力和实时健康过滤
  -> 强制优先层
  -> 并发硬限制
  -> 价格、昨日可用性、负载和首 Token 延迟动态评分
  -> 近似最高分候选池
  -> 按配置权重和当前负载公平分流
  -> 当前渠道失败后重新选路
  -> 定价分组故障转移
```

价格、昨日可用性、当前负载和昨日平均首 Token 延迟决定渠道是否进入优选候选池；配置权重只决定同档候选之间的长期流量比例。系统不能在每次请求中直接选择评分最高的单一渠道，否则会造成瞬时和持续流量倾斜。

## 2. 目标与非目标

### 2.1 目标

- 管理员可以独立新增、修改和删除命名策略，并设置价格、可用性、负载和首 Token 延迟权重。
- 每个定价分组必须引用一个现有策略，同一策略可以被多个分组复用。
- 强制优先配置具有明确且可解释的最高优先级。
- 用有效价格、前一天可用性、当前并发负载和昨日平均首 Token 延迟计算动态优先级。
- 在多个质量接近的渠道之间按权重稳定分流。
- 防止低价或高可用渠道长期独占流量并被快速打满。
- 渠道失败时只淘汰与错误作用域对应的候选，不因单渠道故障直接淘汰整个定价分组。
- 多个定价分组可用时，先选择定价分组，再选择其中的渠道，避免渠道数量影响分组获得流量的概率。

### 2.2 非目标

- 不把所有规则压缩成一个不可解释的全局分数。
- 不让普通路由顺序覆盖所选策略。普通顺序只用于最终确定性打破平局。
- 不使用仅供压测估算的 `cost_factor` 代替运行时有效价格。
- 不根据单次成功或没有样本的数据直接认定渠道为 100% 稳定。
- 不保证已熔断、凭证失效、模型不支持或并发已满的渠道获得探索流量。

## 3. 术语和作用域

- **有效价格**：当前请求模型在候选渠道上的实际计费价格，包含模型价格、渠道价格倍率和币种换算。
- **前一天可用性**：前一个自然日有效探测样本计算出的成功率，并经过样本量校正。
- **当前负载**：渠道当前已用并发与最大并发的比值。
- **配置权重**：同档候选之间期望的长期流量比例，不是硬优先级。
- **强制优先**：管理员显式配置的硬分层规则，任何动态分数都不能跨越该层级。
- **近似最高分候选池**：与当前最高分差距不超过阈值、可以共同承接正常流量的渠道集合。

策略配置虽然位于“定价分组”页面，但必须明确作用域：

- 只有一个定价分组参与请求时，策略用于选择该分组内的渠道。
- API Key 允许多个定价分组时，先对分组进行一次选择，再在选中分组内选择渠道。
- 跨分组选择不能把所有渠道直接合并成一个池，否则渠道较多的分组会天然获得更多流量。

## 4. 调度阶段

### 4.1 候选过滤

以下条件属于硬过滤，不参与动态评分：

1. API Key 和用户有权使用该定价分组。
2. 渠道已启用，且支持请求模型和请求路径。
3. 渠道计费配置完整，能够算出当前请求的有效价格。
4. 渠道未处于打开的熔断状态。
5. 渠道没有凭证失效、模型不支持等当前已知的硬故障。
6. 当前并发没有达到最大并发。

评分较高不能覆盖任何硬过滤条件。

### 4.2 强制优先

强制优先由管理员定义，不由系统计算。建议使用顺序值表达层级，数字越小越靠前：

```text
1 -> 2 -> 3 -> 普通候选
```

如果当前最高强制优先层仍有可用渠道，只在该层内执行动态评分和公平分流。该层候选全部不可用后，才进入下一层。

普通 `priority` 不再作为动态策略之前的硬层级；如需保留，只作为所有动态条件相同时的稳定排序字段。否则“价格优先”无法保证价格是最重要的动态因素。

### 4.3 并发硬限制

当前并发达到最大并发的渠道直接排除。真正发送请求之前必须原子预占并发：

1. 根据最新数据选择渠道。
2. 原子预占该渠道的一个并发名额。
3. 预占失败时移除该候选并立即重选。
4. 请求结束后释放名额。

普通 Relay 和任务 Relay 在控制器的上游调用边界执行这次原子预占；Midjourney 使用独立的代理处理链，在其直接 HTTP 请求边界执行一次预占。两条链路互不重复计数。

评分不能代替并发预占，因为多个请求可能同时读取到相同的旧负载。

## 5. 特征计算

各项特征统一归一化为 `0..1`，数值越大越优先。

### 5.1 价格分数

价格必须按当前请求模型计算。令：

- `price`：当前候选渠道的有效价格；
- `min_price`：当前候选集合中的最低有效价格；
- `price_gap = price / min_price - 1`。

请求模型（计费上下文中的 `OriginModelName`）优先于渠道的上游模型映射；映射只在请求模型没有价格或倍率配置时作为后备。显式配置为 `0` 的模型价格表示免费，必须参与最低价格基线，不能被当作“未配置”而回退到倍率。

路由配置中的 `cost_factor` 只能作为有效价格的显式修正系数，不能替代当前模型价格、渠道倍率或币种换算得到的运行时价格。

建议增加 3% 的同价容差，并在价格高出最低价 20% 时达到最大惩罚：

```text
price_gap <= 0.03:
  P = 1

price_gap > 0.03:
  P = 1 - clamp((price_gap - 0.03) / (0.20 - 0.03), 0, 1)
```

采用价格容差的原因是：同一定价分组内渠道价格通常差异有限，不应让 1% 左右的价格差持续压过明显的可用性或负载差异。

### 5.2 前一天可用性分数

不能直接使用原始成功率。样本很少时，将观测结果向 95% 的中性先验收缩：

```text
confidence = min(valid_samples / 100, 1)
A = confidence * observed_success_rate
    + (1 - confidence) * 0.95
```

示例：

- 昨日 1 次成功：不会直接得到 100% 的可信可用性。
- 昨日 100 次以上有效样本：基本采用实际成功率。
- 没有样本：使用 95% 中性值，而不是当前逻辑中的 100%。

前一天可用性是慢速质量指标。当前连续超时、429、5xx 和熔断状态仍通过实时过滤或短期惩罚处理，不能等待第二天的统计结果。

### 5.3 当前负载分数

已配置最大并发时：

```text
utilization = clamp(current_concurrency / max_concurrency, 0, 1)
L = 1 - utilization
```

规则：

- `utilization >= 1`：硬过滤。
- `utilization >= 0.7`：分流阶段施加明显负载惩罚。
- 未配置最大并发时按产品默认值 `1000` 处理；因此仍会参与并发硬限制和负载评分。管理员可以显式设置更合适的上限。

### 5.4 昨日平均首 Token 延迟分数

昨日平均 TTFT 使用流式消费日志中的 `other.frt`（毫秒）计算。当前候选集合中的最低有效 TTFT 作为基线：

```text
T = clamp(min_ttft / ttft, 0, 1)
```

没有有效样本的渠道不参与基线计算，使用中性先验 `T = 0.5`，避免缺失数据直接获得最高或最低分。

### 5.5 配置权重

渠道路由权重不加入价格、可用性、负载和首 Token 延迟的基础分数，而在候选池内决定流量比例；策略目录中的四项特征权重用于第 6 节的基础动态分数：

- 未配置时默认为 `1`。
- 正数表示长期相对比例，例如 `1:3` 期望获得约 `1:3` 的流量。
- 建议限制可配置比例差，例如最大不超过 `1:10`。
- `0` 应明确表示不承接普通流量，不能隐式转换成 `100` 或额外加一个固定值。

## 6. 可复用策略

基础动态分数为：

```text
S = 100 * (w_price * P + w_availability * A + w_load * L + w_ttft * T)
```

### 6.1 策略目录与绑定

策略定义与定价分组绑定分开存储：

- 策略 ID 是内部稳定标识，不作为管理员编辑字段。
- 策略名称不能为空或重复，修改名称不会改变已有分组绑定。
- 四项权重必须是有限的非负数，且总和必须为 100。
- 旧配置缺少 `ttft_weight` 时按 `0` 兼容，升级后保存会补齐该字段。
- 每个定价分组必须绑定一个存在的策略。
- 被定价分组引用的策略不能删除；先修改对应分组绑定后才能删除。
- 新增、编辑、删除策略与分组绑定通过同一个定价分组配置原子保存，不能产生半更新状态。

持久化结构如下：

```json
{
  "strategies": {
    "strategy_id": {
      "name": "均衡",
      "price_weight": 40,
      "availability_weight": 40,
      "load_weight": 20,
      "ttft_weight": 0
    }
  },
  "group_bindings": {
    "default": "strategy_id"
  }
}
```

### 6.2 初始策略

新配置会创建以下初始记录，它们可以像其他策略一样修改或删除，不构成封闭枚举：

| 策略 | 有效价格 `P` | 昨日可用性 `A` | 当前负载 `L` | 首 Token 延迟 `T` |
| --- | ---: | ---: | ---: | ---: |
| 价格优先 | 65% | 20% | 15% | 0% |
| 均衡 | 40% | 40% | 20% | 0% |
| 稳定 | 20% | 60% | 20% | 0% |

#### 价格优先

- 价格是最重要的动态因素。
- 3% 以内视为同一价格档，改由可用性、负载和权重分配流量。
- 低价渠道达到并发上限或进入熔断后立即排除，不等待其恢复。
- 价格优势不能突破强制优先层、权限或实时健康过滤。

#### 均衡

- 价格与昨日可用性具有相同权重。
- 当前负载占 20%，用于主动把流量引导到仍有容量的近似候选。
- 适合作为默认策略，因为它不会为了很小的价格差长期使用明显不稳定的渠道。

#### 稳定

- 昨日可用性占 60%，是主要动态因素。
- 价格仍占 20%，避免可用性相近时无视成本。
- 实时熔断和当前负载仍是必要约束；昨日稳定不代表当前一定可用。

以上只是初始化建议值。上线后应根据真实监控数据校准，不应按单日波动频繁修改。

## 7. 防止流量倾斜

### 7.1 近似最高分候选池

不直接选择唯一最高分渠道。正常候选池采用：

```text
S >= max_score - score_tolerance
```

初始建议：

- `score_tolerance = 5`。
- 当候选价格差全部在 3% 容差内时，可扩大到 `8..10`。
- 候选池只剩一个渠道时允许由它承接全部当前流量。

### 7.2 有效分流权重

候选池内计算：

```text
load_factor = max(0.25, (1 - utilization) ^ 1.5)
score_factor = exp((S - max_score) / temperature)
effective_weight = configured_weight * load_factor * score_factor
```

其中：

- `configured_weight` 决定管理员期望的长期比例。
- `load_factor` 主动减少高负载渠道继续被选中的概率。
- `score_factor` 让较高分渠道获得更多流量，但不会让其他近似候选概率变为零。
- `temperature` 控制分数差对概率的影响，初始值可设为 `5`，与候选池容差共同调优。

### 7.3 公平调度

推荐在候选池内使用带记账的平滑加权轮询或 Deficit Round Robin，而不是每次独立加权随机：

- 权重决定长期流量比例。
- 当前负载动态修正本轮有效权重。
- 暂时少分配的健康渠道会逐步得到额度补偿。
- 避免独立随机在短窗口内连续命中同一渠道。

如果首版只能使用加权随机，必须增加滚动窗口占比修正，不能只依赖长期数学期望。

### 7.4 流量占比与探索

在至少有两个健康候选时，建议采用以下初始保护值（滚动占比账本与探索流量暂不在首版开启）：

- 单渠道滚动 5 分钟正常流量占比上限：70%。
- 健康但不在优选候选池中的渠道探索流量：合计 5%。
- 只有一个可用渠道时不执行 70% 上限。
- 已熔断、凭证失效、模型不支持或并发已满的渠道不获得探索流量。

探索流量用于持续获得质量样本，避免新渠道或历史低分渠道永远无法证明已经恢复。探索请求仍需计入并发、错误率和熔断统计。

### 7.5 多实例并发一致性

进程内原子计数只能防止单实例过载。多实例部署时必须使用 Redis 计数器、带过期租约的信号量或其他共享并发控制；否则各实例都会认为渠道仍有剩余容量，合计并发可能突破上限。

首版采用进程内原子计数作为快速保护。多实例部署时推荐补充两层控制：

1. 进程内计数作为快速保护和本地调度信号。
2. Redis 作为跨实例并发硬限制，并通过租约过期处理进程异常退出。

## 8. 多定价分组选择

API Key 允许多个定价分组时采用两级调度：

1. 在每个分组内选出当前代表渠道，或聚合计算分组价格、可用性和剩余容量。
2. 使用同一策略在分组层选择一个定价分组。
3. 在选中分组内部重新读取最新状态并选择具体渠道。

分组层指标建议：

- 价格：该分组当前健康候选中的最低有效价格，或根据组内有效分流权重计算的预期价格。
- 可用性：按组内预期流量比例加权的可用性，不能简单取最大值。
- 负载：组内可用并发容量占总容量的比例。

只有 API Key 明确允许跨定价分组故障转移时，当前分组耗尽后才进入下一个分组。用户手动指定单一分组时不能擅自跨组。

## 9. 失败、重试与降级

### 9.1 失败作用域

- `429`、超时、`5xx`：淘汰或短期惩罚当前渠道，重新计算剩余候选。
- 凭证失效、模型不存在、渠道配置错误：当前渠道进入更长熔断。
- 客户端参数错误、内容策略拒绝：终止请求，不切换渠道。
- 能明确定位到 provider 级故障时，可以同时惩罚该 provider 的关联候选，但必须由结构化错误作用域决定，不能用错误文本猜测。

一个渠道失败不能直接淘汰整个定价分组。只有组内候选全部不可用或重试预算耗尽时，才判断是否跨组。

### 9.2 重算规则

每次切换渠道时都重新读取以下易变数据：

- 熔断状态；
- 当前并发和可预占容量；
- 当前请求已尝试渠道集合；
- 滚动窗口流量占比；
- 当前总尝试次数和剩余时间预算。

同一次客户端请求不能再次选择已经确认失败的渠道，除非错误规则明确允许在当前渠道内重试，且尚未耗尽该渠道的尝试次数。

### 9.3 预算

调度必须同时限制：

- 单渠道最大尝试次数；
- 单次客户端请求最大总尝试次数；
- 单次客户端请求总时间预算。

任一总预算耗尽后立即返回最终错误，不能继续遍历全部渠道。

## 10. 数值示例

假设经过样本量校正后有三个候选渠道：

| 渠道 | 有效价格 | 可用性分数 | 当前并发占比 | 配置权重 |
| --- | ---: | ---: | ---: | ---: |
| A | 0.90 | 99.0% | 80% | 1 |
| B | 0.96 | 97.0% | 35% | 2 |
| C | 1.02 | 99.5% | 20% | 1 |

假设归一化结果为：

本示例沿用初始策略的 `ttft_weight = 0`，因此省略 `T` 列；配置 TTFT 权重后，按第 5.4 节的基线规则追加该项。

| 渠道 | `P` | `A` | `L` |
| --- | ---: | ---: | ---: |
| A | 1.00 | 0.990 | 0.20 |
| B | 0.80 | 0.970 | 0.65 |
| C | 0.60 | 0.995 | 0.80 |

得到基础分数：

| 策略 | A | B | C | 主要结果 |
| --- | ---: | ---: | ---: | --- |
| 价格优先 | 84.8 | 80.4 | 71.9 | A、B 为主要候选；A 价格最低，但高负载会降低其实际分流权重 |
| 均衡 | 83.6 | 83.8 | 79.8 | 三者质量接近；B 因负载较低且权重为 2 获得较多流量 |
| 稳定 | 83.4 | 87.2 | 87.7 | B、C 为主要候选；A 因高负载和稳定性优势不足而降权 |

该示例只展示基础评分。最终流量比例还要经过候选池、负载因子、配置权重和平滑调度，以及原子并发预占修正，因此不能把最高基础分理解为 100% 流量。滚动流量上限和探索流量属于后续增强，首版不会虚构这些账本。

## 11. 配置建议

定价分组表单至少需要配置：

| 配置 | 建议默认值 | 说明 |
| --- | ---: | --- |
| 分组策略 | 均衡 | 从策略目录中选择一个现有策略 |
| 策略权重 | 40 / 40 / 20 / 0 | 价格、可用性、负载和首 Token 延迟四项总和为 100 |
| 分数容差 | 5 | 决定近似最高分候选池范围 |
| 温度 | 5 | 决定候选池内分数差对分流概率的影响 |
| 单渠道流量上限 | 后续增强 | 首版不启用滚动占比账本 |
| 探索流量 | 后续增强 | 首版不主动把流量分给非首选候选 |
| 价格同档容差 | 3% | 容差内不放大微小价格差 |

首版 UI 在定价分组表格的“分组监控”后提供策略选择，并在下方“策略设置”中提供策略 CRUD。分数容差、温度等其余参数仍使用系统默认值。强制优先顺序、渠道权重和最大并发继续作为渠道级配置。

## 12. 监控与校准

至少按策略、定价分组和渠道记录：

- 请求命中次数和流量占比；
- 基础分数、入选候选池原因和最终有效权重；
- 当前并发、并发利用率和并发预占失败次数；
- `429`、超时、`5xx` 和熔断次数；
- 成功率、P95 延迟和平均有效价格；
- 渠道切换次数、最终耗尽次数和平均尝试次数；
- （后续增强）探索流量的成功率和恢复判定结果。

校准周期建议至少按周评估，重点检查：

1. 价格优先是否确实降低平均成本。
2. 稳定策略是否降低最终错误率和渠道切换率。
3. 单渠道 5 分钟流量占比是否频繁触顶。
4. 并发预占失败是否说明负载数据过期或容量配置过低。
5. （后续增强）探索流量是否足以发现渠道恢复，又没有显著损害总体成功率。

## 13. 验收标准

1. 强制优先层可用时，普通候选不会越级获得流量。
2. 强制优先层内仍遵守模型能力、熔断和并发硬限制。
3. 任意合法的自定义策略 ID 和权重都会参与实际评分，不会回退到初始策略。
4. 3% 价格容差内，微小价格差不会持续压过明显的可用性或负载差异。
5. 样本不足的渠道不会因为一次成功而被认定为 100% 稳定。
6. （后续增强）两个以上健康候选存在时，单渠道不会长期超过配置的滚动流量上限。
7. 配置权重为 `1:3` 且其他条件一致时，长期流量比例接近 `1:3`。
8. 渠道达到最大并发后不再收到新请求，预占失败会触发即时重选。
9. 多实例合计并发不会突破渠道最大并发。
10. 单渠道失败只淘汰相应候选；组内候选耗尽后才按 API Key 权限决定是否跨组。
11. 达到总尝试次数或总时间预算后，不再继续切换渠道。
12. 调度日志可以解释一次请求为何进入某个分组、候选池并最终选择某个渠道。
13. 策略名称唯一、权重总和为 100、分组引用完整；被引用的策略不能删除。

## 14. 实施前待确认项

以下参数应在实现前通过压测和生产流量样本确认：

- 前一天可用性统计的有效样本定义和最小样本阈值。
- 价格同档容差 `3%` 是否适合所有模型类型。
- 分数容差 `5` 和温度 `5` 的初始值；流量上限 `70%` 与探索流量 `5%` 需在后续增强实现时再确认。
- 未配置最大并发时是否要求补齐配置，或使用经过验证的软容量估计。
- 分组层使用最低有效价格还是预期加权价格。
- 跨实例并发控制采用 Redis 计数器还是租约信号量。
- 平滑加权轮询与 Deficit Round Robin 的最终实现选择。
