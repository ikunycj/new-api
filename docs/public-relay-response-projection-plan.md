# 用户侧渠道信息隐藏与错误白名单方案

**状态：** 核心代码已实现并通过测试；尚未部署，保留少量特殊资源与运行态验收项。

**更新日期：** 2026-11-13。

**本次核对基线：** `feature/new-master@5c31c4a995ba5215679f453dbdc52f1d0d45cad2`。这是本轮工作区状态，不沿用此前其他分支的实现结论；开工前复核分支。

## 1. 目标与确定规则

用户看到的是统一的渠道展示身份：

```json
{
  "channel_id": 1,
  "channel_name": "auto"
}
```

- `1` 和 `auto` 都是展示占位值，不对应数据库中的真实渠道 1，也不表示实际执行了自动选路。
- 日志存储、服务端日志、渠道缓存、请求上下文、重试、封禁和计费继续使用真实渠道数据，不能在这些位置写入占位值。
- 在服务端生成面向用户的响应副本时才替换；不能只在前端把文字遮住，而让浏览器网络响应或 API 客户端继续收到真实信息。
- 适用于用户的模型调用、用户日志/Token 日志、任务/Midjourney 查询及相关详情。后台授权的管理接口继续展示真实诊断信息；管理员访问普通用户接口时也使用公共视图。
- 这是对之前“渠道名使用定价分组名”的明确替代：渠道显示为 `auto`，定价分组仍是独立的业务字段，不一并改成 `auto`。
- 已有渠道身份字段一律替换；原本没有渠道字段的标准协议不强行增加字段，例如 Claude 错误体仍保持其协议结构。

## 2. 字段处理清单

以下表格针对已知业务字段和错误对象，不是对所有响应键名进行全局正则替换。正常生成内容、用户输入、工具输出和引用中的同名字段不机械处理。

### 2.1 渠道身份与关联信息

| 字段/位置 | 用户响应 | 内部记录 |
| --- | --- | --- |
| `channel_id`、任务/Midjourney 的 `channel_id` | 数值 `1`，不是字符串 `"1"` | 保留真实 ID |
| 用户日志顶层 `channel` | 数值 `1`；当前 Log 的 JSON 字段名就是 `channel`，不能漏掉 | 保留真实 ID |
| `channel_name`，或明确表示渠道名称的字段 | 字符串 `auto` | 保留真实名称 |
| `other.channel_id`、`other.channel_name` | 公开结构需要保留时同样固定为 `1` / `auto`，无用途的重复字段直接省略 | 保留原值 |
| `channel_type`、真实渠道类型编号 | 省略，不伪造为类型 1，因为类型 1 也有实际协议含义 | 保留 |
| `error_ref` | 省略，不改写为 `305001-CH1`；保留后半段占位仍会泄露前半段内部分类 | 保留 |
| `upstream_request_id`、供应商诊断/追踪标识 | 省略 | 保留，使用本地 request ID 关联 |
| 上游 `base_url`、内部 endpoint、代理地址、Key/账号/池标识 | 不进入用户 DTO | 按原有权限与凭证掩码规则保留 |
| 公开模型目录 `owned_by` | 建议固定为 `gateway`，停止依据实际候选渠道推导；它不是渠道名，不填 `auto` | 内部渠道归属不变 |

当前源码依据：[错误类型](../relaykit/types/error.go)、[日志结构与 formatUserLogs](../model/log.go)、[任务 DTO](../dto/task.go)、[TaskModel2Dto](../relay/relay_task.go)、[模型目录](../controller/model.go)。

### 2.2 错误对象

| 字段 | 用户响应建议 |
| --- | --- |
| `message` | 按第 4 节白名单处理：命中状态码或任一错误字段的模糊规则后透传三个字段，或返回自定义三个字段；未命中时使用统一提示加客服信息 |
| `code`、错误对象中的 `error_code` | 未获放行时统一为 `service_error`；命中后按透传规则保留原值，或使用管理员配置的自定义值 |
| `type` | 未获放行时使用通用 `server_error`；命中后按透传规则保留原值，或使用管理员配置的自定义值。本地参数/认证错误保留其正常协议类型 |
| `param` | 保留已确认属于用户请求参数的字段名；上游任意附加内容不透传，无法确认时为空 |
| `source`、`error_source`、`source_code` | 省略，避免暴露官方直连/中间渠道及原始错误归属 |
| 内部 `stable_code` | 省略，它是内部分类而不是用户需要的公开业务码 |
| `category`、`failure_scope`、错误对象的 `action` | 省略，避免暴露账号、渠道或供应商层级。正常任务的业务 `action` 不受此规则影响 |
| `retryable`、`attempt_count` | 省略，避免暴露内部重试策略与尝试次数；不把次数伪造为 1 |
| `cause` | 整个字段省略，不保留嵌套渠道身份、原始状态和错误码 |
| 错误 `metadata`、原始错误 body、堆栈 | 省略；白名单不授权整个对象透传 |
| 本地 `request_id` | 保留真实值，支持用户提供关联 ID 排障 |
| HTTP 状态码 | 建议保持现有最终状态处理，与 JSON 的业务码分开；不因本方案改成 200，也不新增复杂的状态分类重写 |

“固定渠道身份”优先于错误白名单：即使命中白名单，也只能得到 `1 / auto`，不能重新带出真实渠道字段。允许透传的自由文本仍需管理员确认适合公开；只按错误码命中并不能证明整段 message 没有渠道名称。含真实渠道信息的消息应配置自定义内容，不承诺靠关键词替换自动清理所有原文。

### 2.3 用户日志中的 `other`、正文和失败原因

`other` 当前是 JSON 字符串，用户可以自行解码；不能因为前端不展示它就保留内部数据。读出后解析为独立对象，构造公共字段集合，再序列化回既有字符串类型，不改历史存储。

| 字段/内容 | 用户响应处理 |
| --- | --- |
| `other.admin_info`、`other.audit_info` | 整体省略，包括 `use_channel`、`is_multi_key`、`multi_key_index`、亲和性/Key 指纹等内部信息；这些字段当前已部分过滤，继续保持 |
| `other.error_source`、`source_code`、`stable_code`、`retryable`、原始内部 `status_code` | 省略；不允许用户从日志绕过错误响应的隐藏 |
| `other.error_code`、`other.error_type` | 如用户详情需要，只写入公共错误码和类型；不需要时省略 |
| `other.upstream_model_name`、`other.is_model_mapped` | 省略，只保留用户请求模型名 |
| `other.request_conversion`、表示最终上游格式的 `other.claude` | 省略，避免透露实际转发协议；前端正常协议/计费展示改用公开请求与用量字段 |
| `other.po`、`other.is_system_prompt_overwritten` | 省略，隐藏渠道参数覆写和提示词注入细节 |
| `other.stream_status`、原始 `reject_reason` | 内部诊断不公开；需要展示失败状态时提供不含原文的结果说明，不透传内部错误数组 |
| 渠道错误日志 `content`、退款中的原始 `reason` | 在用户读取时套用同一公开消息规则；保留失败/退款事实与金额，不回显原始渠道错误 |
| 普通消费、充值、登录等非渠道错误日志 | 保留正常业务内容，不一律替换成异常提示 |
| 价格、公开倍率、token/缓存用量、费用、账务来源、任务 ID、时间和耗时 | 保留用于用户核对。若某扩展字段实际保存采购侧成本或渠道配置，只保留其面向用户的计费部分 |

字段来源可核对 [service/log_info_generate.go](../service/log_info_generate.go)、[processChannelError](../controller/relay.go) 和 [service/task_billing.go](../service/task_billing.go)。新加入的内部诊断字段不得自动进入用户侧 `other`；异常或无法解析的历史 `other` 不原样透传，仅保留可确定的公开字段并记录解析问题。

### 2.4 任务、资源与正常协议字段

- Task/Midjourney 的渠道 ID 按第 2.1 节固定；已有渠道名称固定为 `auto`。只有渠道 ID 的用户界面也显示 `auto`，不请求真实 `/api/channel/1` 取得名称，不显示“渠道 #1”作为真实身份。
- 失败任务的 `fail_reason` / `failReason` 与嵌套供应商错误使用公开消息；历史数据无法确认原始码时使用统一提示，不从包装后的长字符串猜码。成功任务仍保留成功状态和结果。
- `properties.upstream_model_name` 隐藏；`properties.origin_model_name`、正常输入、进度、输出和必要操作参数保留。`data` / `properties` 按各协议明确结构过滤内部字段，不整块丢弃，也不对任意用户内容做全局替换。
- 用户请求模型名、公开品牌、定价分组 key、任务 `platform` / `action` 等业务含义不等于真实渠道，不能全部改成 `auto`；只有实际承载内部渠道身份的值才隐藏。
- 本地 task ID、正常 response/tool/call ID 和多轮引用保持功能。若确认某标识编码了渠道信息，需建立可回查的公共映射，不能简单把所有 ID 改为 1。
- 视频任务和 Midjourney 图片优先使用现有网关代理地址；Suno 音频和 Midjourney 视频等没有统一网关代理的资源仍需单独审计。不能把域名直接替换为 `auto` 或删除成功结果；若实际发现这类地址，需要另行确认代理/转存范围和成本。本轮不默认新增全量媒体代理。

### 2.5 响应头

- 移除公共响应中的 `X-Error-Source`、`X-Error-Source-Code`、`X-Error-Stable-Code`、`X-Error-Ref`、`X-Error-Retryable`，并阻止上游同类诊断头透传。
- 移除 `X-Upstream-Request-Id`、供应商追踪头，以及包含真实渠道的 `Server`、`Via`、`Location` 等值；不新增一组假的渠道诊断头。
- 保留本地 `X-Oneapi-Request-Id`、正确的 Content-Type、CORS、媒体范围请求和 WS 握手所需的协议头。上游头的准入按用途审核，不无差别清空本服务的头。
- 过滤发生在首次写出/flush 之前；不能等响应已经发给用户后再删除头。

## 3. 公开视图与内部数据严格分离

```text
真实渠道结果 → 原始日志、重试、计费和内部记录
                         ↓
                 构造独立用户响应
          渠道占位 + 错误白名单 + 字段过滤
                         ↓
                  用户页面 / API
```

1. 不改渠道表、日志表或缓存中的渠道 ID/名称，不修改 `c` 中真实的 `channel_id`，不全局修改供重试和计费使用的 `NewAPIError`。
2. 用户日志和任务查询生成公共 DTO 副本；处理 map、slice 和嵌套结构时，不让删除字段或替换值影响共享原对象。不要新增全局 `MarshalJSON`，否则管理员和内部日志也会被错误改写。
3. 老日志读时处理即可立即得到同一展示规则，不迁移历史日志；管理员随后查询同一记录仍应看到真实渠道。
4. 用户日志搜索需同时移除真实渠道 ID、名称和上游 request ID 的检索能力。当前 `applyLogKeywordFilter` 存在内部渠道和上游请求 ID 匹配，需区分用户查询与管理员查询，防止从命中数量反查渠道。
5. 前端用户渠道筛选/详情跳转应去掉或仅显示不可操作的 `auto`。展示值 `1` 绝不翻译成 SQL 的 `channel_id = 1`，也不能授予对真实渠道 1 的读写权限；用户提交内部渠道查询参数应按公开接口契约拒绝。管理员渠道查询保持原有权限和能力。
6. 若用户可见接口包含渠道选项或聚合维度，应只暴露一个公共 `1 / auto` 展示维度，不能按真实渠道返回多个同名条目而泄露渠道数量。

## 4. 渠道错误拦截与白名单

渠道错误只做一层统一拦截，覆盖所有渠道返回的 HTTP 4xx、5xx。白名单是唯一的原错误信息公开例外，不再按余额、账号池、凭证、限流等运营原因逐类映射文案，也不再预设全部转换为 503。

| 情况 | 对用户的处理 |
| --- | --- |
| 未配置白名单，或错误未命中白名单 | 返回第 5 节统一提示，隐藏原渠道错误信息和未获放行的错误码 |
| 命中白名单，处理方式为“透传” | 允许返回规则放行的原错误信息；不透传整个原始错误对象 |
| 命中白名单，处理方式为“自定义返回内容” | 使用管理员填写的内容，不拼接原渠道错误信息 |

拦截默认强制生效，没有“全部透传”开关；白名单为空表示所有范围内的渠道错误使用统一提示，不代表关闭保护。

白名单支持两类匹配：HTTP 状态码精确匹配，以及对 `error.code`、`error.type`、`error.message` 任一字段进行不区分大小写的包含匹配。命中后只投影 `error` 对象的三个字段；第 2、3 节的身份替换与内部字段过滤始终生效。日志读取、任务失败详情和已识别的流式错误消息也不能通过另一个显示出口回显同一渠道原文；复用公共消息逻辑，不新增一套按运营原因分类的规则引擎。

## 5. 统一提示与客服信息

未命中白名单时，严格使用用户指定文案：

> 服务暂异常，大概率是临时错误，请重试，如多次重试无效，请联系管理员

随后追加“站点与品牌 → 系统信息 → 客服信息”的实际配置内容，格式为：

```text
服务暂异常，大概率是临时错误，请重试，如多次重试无效，请联系管理员
{CustomerService 的实际内容}
```

- 复用现有 `CustomerService` 配置，不新增第二份客服配置，不输出花括号占位符。
- 客服信息按原有纯文本内容附加，保留有意义的换行；不当 HTML 执行，不进行模板求值。
- 客服信息为空时，仅返回固定提示，不虚构联系方式，也不添加空括号。
- 配置更新后，后续请求按现有选项刷新机制使用新内容，无须重启；多实例遵循现有同步周期，不承诺瞬时全节点生效。
- 本地 `X-Oneapi-Request-Id` 继续保留用于排障，不将渠道编号或上游 request ID 拼到文案中。

已核对的配置入口：前端 [system-info-section.tsx](../web/default/src/features/system-settings/general/system-info-section.tsx) 使用 `CustomerService`；后端 [controller/misc.go](../controller/misc.go) 从 `common.OptionMap["CustomerService"]` 返回现有客服文本。

## 6. 设置入口与规则编辑

新增菜单/页面名称：**渠道白名单**。说明文字明确这是“允许公开的渠道错误规则”，不是选择某几个渠道免于保护。

现有导航中“安全与限制”和“控制台内容”是并列分组，并非父子关系。渠道错误属于对外错误安全策略，入口放在：

```text
系统设置 → 安全与限制 → 渠道错误白名单
```

不为新增这个页面重排整个设置导航。使用现有表单、增删规则和保存交互，不添加规则脚本、正则表达式或复杂条件编辑器。

| 字段 | 内容 |
| --- | --- |
| 匹配项 | HTTP 状态码 / 错误信息模糊匹配 |
| 匹配值 | 4xx/5xx 状态码，或匹配 `error.code`、`error.type`、`error.message` 的文本 |
| 返回方式 | 透传 / 自定义返回内容 |
| 自定义 `error.code` | 选择自定义时必填 |
| 自定义 `error.type` | 选择自定义时必填 |
| 自定义 `error.message` | 选择自定义时必填 |

以下是匹配规则：

- HTTP 状态码规则只接受 `400` 到 `599`，按最终 HTTP 状态码精确匹配，例如 `429`、`502`、`503`。
- 错误信息规则对 `error.code`、`error.type`、`error.message` 三个字段分别做不区分大小写的包含匹配，任一字段命中即可拦截。
- 每条规则只有一种匹配项；匹配到任何一条即可按该条规则处理。
- 透传返回原始 `error.code`、`error.type`、`error.message` 三个字段。
- 自定义规则返回管理员填写的三个字段，不拼接原始错误内容。
- `upstream_exhausted` 等网关内部错误分类只留在内部日志、重试和运维分类中，不作为用户配置项的 HTTP 状态码替代物。
- 即使命中白名单，渠道 ID/名称也固定为 `1 / auto`，错误 cause、metadata、`error_ref` 和内部诊断响应头也不放行。

管理员选择透传，就明确允许该条匹配信息公开；不能再用隐藏规则悄悄把已放行消息替换。页面简短提示“透传内容会对用户可见”，不增加重复确认流程。

## 7. 后端接入边界与响应示例

处理链路保持简单：

```text
接收渠道错误并保留原始状态/错误码/错误信息
    → 现有日志、重试、封禁、退款等处理
    → 最终准备返回用户时匹配白名单
    → 透传允许的信息 / 自定义消息 / 统一提示 + 客服信息
```

- 识别对象是渠道返回的错误，不是本地用户登录、Token 鉴权、参数校验、用户自身余额不足等错误；这些维持现有契约。
- 覆盖渠道原始 HTTP 状态为 400–599 的响应，不按渠道类型另设豁免。判定使用渠道状态码重映射前的状态，避免渠道映射把错误变成 200 后绕过保护。
- 原始错误码和消息在上游解析边界保存。匹配前不能拼入 `metadata`、原始 body、request ID 或“所有渠道重试失败”等包装文字；当前 `WithOpenAIError` 和耗尽包装存在这些处理，需要保留匹配用的原始值。
- 多次重试后仍失败时，匹配最终实际渠道失败的信息；内部记录不替换成用户提示，重试/扣费/退款顺序不变。
- 非结构化错误体、缺少错误码/消息的错误，也会进入未命中处理；不通过包含匹配放行整段 HTML 或原始 HTTP body。
- 统一的是错误内容。建议保持当前最终 HTTP 状态处理，不新增 401/429/503 分类重写；具体错误码字段的匹配和公开范围见第 10 节待确认项。
- 继续按 OpenAI、Claude、Gemini、Task 的既有响应格式写出，不把全部协议改成同一个 JSON。
- 所有返回渠道 4xx/5xx 的同步出口，包括主 Relay、Task、Midjourney、媒体代理的取回错误，调用同一拦截逻辑；不只修改聊天完成接口。
- 尚未开始流式/WS 输出时的渠道 HTTP 错误也遵循同一规则；已经发送数据的连接不能重写 HTTP 状态或追加普通 JSON，沿用协议错误写出方式。

字段隐藏覆盖成功和失败的用户视图，包括历史日志和任务。渠道 HTTP 4xx/5xx 按白名单拦截；上游在 HTTP 200 内发送的已识别错误事件，也应在转发前套用公共错误内容与字段规则，不能只等 controller 的最终 error。网络失败没有可匹配的供应商错误码时，公开消息用统一提示，原异常留在内部。正常生成正文不进行通用扫描改写。

以下为未命中白名单时的建议公开响应，示例中的客服联系方式为占位说明，不代表实际配置：

```http
HTTP/1.1 503 Service Unavailable
Content-Type: application/json; charset=utf-8
X-Oneapi-Request-Id: req_example_001

{
  "error": {
    "message": "服务暂异常，大概率是临时错误，请重试，如多次重试无效，请联系管理员\n示例客服联系方式",
    "type": "server_error",
    "param": "",
    "code": "service_error",
    "request_id": "req_example_001",
    "channel_id": 1,
    "channel_name": "auto"
  }
}
```

本例假设既有最终 HTTP 状态为 503，不表示所有错误都重写成 503。原来的 `cause`、分类码、来源和重试字段均不出现。

用户日志中的单条消费记录示意（其余公开账务字段按原接口保留）：

```json
{
  "type": 2,
  "model_name": "用户请求的模型名",
  "channel": 1,
  "channel_name": "auto",
  "request_id": "req_example_001",
  "quota": 1200,
  "prompt_tokens": 100,
  "completion_tokens": 200,
  "other": "{\"model_ratio\":1,\"group_ratio\":1,\"frt\":320}"
}
```

这里的 `quota` 是示例内部额度数值，不是直接的货币金额；实际用量、费用和时间不因为隐藏渠道而修改。管理接口查询同一记录，仍可得到实际渠道编号、渠道名称及内部诊断字段。

## 9. 执行与验证

执行顺序：确认白名单错误码口径 → 公共对象/身份规则 → 配置和错误拦截 → 用户日志/任务及搜索 → 前端 `auto` 展示和白名单页面 → 定向验证。

重点验证：

1. 白名单为空或未命中，渠道 400、401、429、500、503 等都返回固定提示和当前客服内容，不含原始错误。
2. 命中错误码或错误信息规则，分别验证透传和自定义内容；自定义回复不混入原文。
3. 客服内容更新、为空和多行时表现正确；规则和错误匹配文本不会随公共配置泄露。
4. 重试耗尽、状态码重映射、缺字段和非 JSON 上游错误仍按规则处理，内部日志保持原始内容。
5. 使用至少两个不同真实渠道构造输出，公开 `channel_id` / `channel` 都为数值 1、名称都为 `auto`；cause、metadata、诊断响应头和嵌套 `other` 不泄露原值，白名单只开放约定字段。
6. 本地用户鉴权、参数、额度错误不被误拦截；相关协议格式、重试、计费/退款行为保持原有语义。
7. 管理员增删规则、重复项校验、重新加载后配置持久化，以及对应前端类型和翻译检查。
8. 同一请求的内部错误、数据库日志、管理员响应保持真实渠道；公开对象转换前后内部对象不变，账务和重试无副作用。
9. 历史日志/Task/MJ 查询也使用公共视图；仅失败内容被替换，成功结果、正常状态、费用及请求模型不丢失。
10. 用户关键词和筛选不能反查真实渠道；公开的 1 不会触发真实渠道 1 的详情查询或成为真实路由条件。
11. SSE/WS 已识别错误消息不会绕过公共内容规则；维持事件格式、正常内容和正确的连接终止行为。

仅运行相关测试和必要构建，不默认启动服务或部署，不改 `.env`，不引入 trace 或资源代理。

## 10. 实施边界与剩余工作

**“错误码白名单”具体匹配什么？**

- HTTP 状态码，例如 `400`、`429`、`503`；
- 还是渠道响应体中的业务错误码，例如 `context_length_exceeded`、`invalid_api_key`。

两者含义不同：放行整个 HTTP 400 可能公开该状态下所有不同的错误文本；业务错误码匹配可以只开放某一种错误。本版已选择匹配上游原始业务码，例如 `pool_exhausted`，不匹配 HTTP 状态码或 NewAPI 稳定码。

真实分组名称、产品备注、资源域名可能由管理员配置成供应商名称。当前未读取线上配置，也不默认更名或新增全量媒体代理。若实际存在这样的溯源线索，需要给出具体影响清单再确认处理，不能宣称仅把 ID 和名称换成 `1 / auto` 就消除了所有可能的溯源方式。

本轮已修改业务代码、后端测试和前端设置/展示代码；未修改数据库 schema、`.env`，未部署，也未引入 relay trace。流式 200 内错误事件、Task、Suno 媒体、视频和 Midjourney 特殊出口已有第一版处理；需要在测试环境验证真实上游响应、媒体代理权限和多实例配置刷新，不能把本地测试等同于线上验收。
